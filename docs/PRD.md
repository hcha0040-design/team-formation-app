# PRD: 팀 프로젝트 팀 편성 웹 앱

## 1. 목적

학생들이 팀 프로젝트를 위한 팀을 스스로 편성하는 웹 앱을 만든다. 학생은 팀에 지원하고 팀원은 투표로 받아들인다. 모집을 마감한 뒤 팀이 없는 학생은 AI가 배정안을 내고, 앱이 그 배정안을 규칙으로 검사한 뒤 관리자가 확정한다.

- 배포: Streamlit Community Cloud
- DB: Supabase(PostgreSQL), 테이블 이름은 모두 `tf_`로 시작
- AI: 오픈라우터 텍스트 생성 무료 모델 3개(1차, 2차, 3차)
- 채점: 자동 채점 프로그램이 Streamlit `key`로 화면 요소를 찾아 조작함

## 2. 사용자

| 사용자 | 로그인 | 하는 일 |
|---|---|---|
| 학생 | 학번 + 비밀번호(모두 `1234`) | 팀 목록과 팀원(이름, 주 역할, 보조 역할)을 봄. 팀에 지원함. 내 팀에 들어온 지원에 찬성 또는 거부함 |
| 관리자 | `admin` + `ADMIN_PASSWORD` | 명단 CSV와 팀 수로 처음 상태를 만듦. 모집을 마감함. AI 배정안을 받아 확인하고 확정함 |

- 관리자 계정은 앱이 시작할 때 `ADMIN_PASSWORD`로 만들거나 비밀번호를 갱신한다. 명단을 다시 올려도 남긴다.
- 학생 계정으로는 관리자 기능을 쓸 수 없다.
- 비밀번호는 bcrypt 해시로 저장한다. 비밀번호가 틀리면 로그인되지 않는다.

## 3. 용어

- **역할 6개**: 기획자(PL), 웹 프로그래머(WP), 프론트엔드 디자이너(FD), 테스터(TT), 보고서 작성자(RW), 발표자(PT)
- **주 역할**: 학생마다 1개. 팀 안의 중복을 따지는 기준
- **보조 역할**: 학생마다 0~2개. 필수 포함 역할을 맡을 수 있는지 따질 때만 씀
- **필수 포함 역할**: 기획자와 웹 프로그래머. 확정한 팀마다 서로 다른 학생이 1명씩 맡아야 함(주 역할이나 보조 역할로)
- **막힘**: 지원 단추를 누른 순간 규칙 위반이라 접수하지 않음
- **거절**: 접수되어 대기 중이던 지원이 팀원의 거부, 승인 직전 검사, 모집 마감으로 떨어짐

## 4. 팀 규칙

1. 팀 수는 관리자가 명단을 올릴 때 넣는다(팀1, 팀2, …).
2. 한 팀은 최대 4명이다. 확정한 팀은 모두 2~4명이어야 한다(빈 팀 없음).
3. 주 역할이 같은 학생이 한 팀에 2명 이상이면 안 된다.
4. 확정한 팀마다 기획자와 웹 프로그래머를 서로 다른 학생이 맡아야 한다.

## 5. 기능 요구사항

### 5.1 명단 올리기(관리자)

- 명단 CSV(`student_no,name,main_role,sub_roles`, UTF-8, BOM 있을 수 있음)와 팀 수를 넣고 시작 단추를 누른다.
- 지원, 투표, 팀원, 마감 표시를 모두 지우고, 명단의 학생과 팀 수만큼의 빈 팀을 만든다.
- 값의 앞뒤 공백을 지운다. `sub_roles`는 `;`로 나누고, 비어 있으면 보조 역할이 없다.
- 역할 이름이 6개 밖이거나 열 수가 틀리면 "막힘"과 이유를 보여 주고 아무것도 바꾸지 않는다.

### 5.2 지원(학생)

지원 단추를 누르면 아래 순서로 검사한다. 하나라도 걸리면 "막힘: 이유"를 보여 주고 접수하지 않는다.

| 순서 | 검사 | 막힘 이유 |
|---|---|---|
| 1 | 모집이 마감됨 | 모집이 마감됨 |
| 2 | 이미 팀이 있음 | 이미 팀이 있음 |
| 3 | 결과를 기다리는 지원이 있음 | 결과를 기다리는 지원이 있음 |
| 4 | 팀이 4명임 | 팀이 꽉 참 |
| 5 | 주 역할이 같은 팀원이 있음 | 같은 주 역할의 팀원이 있음 |
| 6 | 필수 포함 역할 자리가 모자람(6.1절) | 필수 포함 역할을 맡을 학생의 자리가 모자람 |

- 1~3에 해당하면 지원 단추를 아예 숨기거나 비활성화한다.
- 통과하면: 빈 팀이면 바로 "승인"(팀원이 됨), 팀원이 있으면 "대기".

### 5.3 투표(학생)

- 팀원은 자기 팀에 대기 중인 지원마다 찬성 또는 거부를 누른다. 한 번 한 투표는 바꿀 수 없다.
- 이미 투표한 지원은 단추를 숨기고 "내 투표: 찬성"처럼 보여 준다.
- 투표할 사람은 **투표하는 때의 팀원 전체**다. 내가 지원한 뒤 다른 지원자가 먼저 팀원이 되면 그 사람도 내 지원에 투표한다.
- 한 명이라도 거부하면 바로 "거절".
- 지금 팀원 모두가 찬성하면 **승인 직전 재검사**(6.2절)를 한다. 통과하면 "승인", 어기면 "거절".
- 아직 투표하지 않은 팀원이 있으면 "대기".
- 결과 안내는 그 지원의 지금 상태(승인, 대기, 거절)를 보여 준다.

### 5.4 모집 마감(관리자)

1. 마감 뒤로는 지원과 투표를 할 수 없다.
2. 대기 중인 지원은 모두 거절한다.
3. 1명뿐인 팀의 학생은 팀에서 빠져 "팀이 없는 학생"이 된다.
4. 팀이 없는 학생의 이름을 관리자 화면에 보여 준다.

### 5.5 배정(관리자)

1. **먼저 규칙을 지키는 배정이 있는지 앱이 직접 찾는다**(6.3절). 없으면 AI를 부르지 않고 "규칙을 지키는 배정이 없음"과 그 이유(예: "팀3에 웹 프로그래머를 맡을 학생이 없음")를 보여 준다.
2. 있으면 1차 모델에게 지금의 팀 구성, 팀이 없는 학생과 그 역할, 팀 규칙을 보내 배정안(JSON)을 받는다.
3. 배정안을 다섯 가지로 검사한다.
   - 팀이 없는 학생이 빠짐없이 배정됨
   - 한 학생은 한 팀에만 배정됨
   - 모든 팀이 2~4명
   - 팀 안에서 주 역할 중복 없음
   - 필수 포함 역할 충족
4. 응답 없음, 120초 넘음, 빈 응답, 오류, 검사 불합격이면 2차, 3차 모델로 넘어간다.
5. 3차 모델까지 실패하면 1단계에서 찾은 배정안을 쓴다.
6. 검사를 통과한 배정안만 관리자에게 보여 준다(학생 이름, 역할, 배정된 팀). 어느 모델이 냈는지, 앱이 직접 찾았는지도 함께 보여 준다.
7. 관리자가 확정하면 DB에 저장한다. 이미 팀에 있는 학생은 옮기지 않는다.

### 5.6 화면

- 학생 화면
  - 로그인한 사람의 이름을 보여 준다.
  - 팀 목록에는 팀원의 이름, 주 역할, 보조 역할이 보인다.
  - 내 팀은 "내 팀"으로 표시하고, 팀이 없으면 "아직 팀이 없음"을 보여 준다.
  - 내 팀에 대기 중인 지원 목록과 투표 단추를 둔다.
- 관리자 화면: 명단 올리기, 모집 마감, 팀이 없는 학생, AI 배정과 진행 안내, 배정안, 확정 단추를 둔다.
- 다른 사람의 변경은 `st.fragment(run_every=...)`로 5초 이하 간격마다 바뀐 부분만 다시 그린다.
- 모든 단추의 결과 안내는 `result` 안에 "승인", "대기", "거절", "막힘" 가운데 하나로 시작한다.

## 6. 핵심 규칙 계산

### 6.1 필수 포함 역할 자리 계산(지원할 때)

```
팀원 + 지원자 = M (n명)
채운 필수 역할 수 = M 안에서 {기획자, 웹 프로그래머}를 서로 다른 학생에게 짝지을 수 있는 최대 수 (0~2)
                   (학생은 주 역할이나 보조 역할에 그 역할이 있으면 맡을 수 있음)
남는 자리 = 4 - n
못 채운 필수 역할 수 = 2 - 채운 필수 역할 수
남는 자리 < 못 채운 필수 역할 수 → 막힘
```

예: 테스터와 발표자만 있는 팀(2명)에 보고서 작성자가 지원하면 남는 자리 1 < 못 채운 2 → 막힘.

### 6.2 승인 직전 재검사

지금 팀원 모두가 찬성해 승인하려는 순간 다음을 다시 검사한다. 하나라도 어기면 "거절"이다.

- 정원
- 주 역할 중복
- 필수 포함 역할 자리(6.1절)

처리 순서는 지원한 순서가 아니라 투표가 끝난 순서다. 그 전에는 대기 중인 지원을 미리 거절하지 않는다.

### 6.3 앱이 직접 하는 배정(완전 탐색)

- 팀이 없는 학생(최대 8명)을 한 명씩 팀에 넣어 보는 백트래킹으로, 다섯 가지 검사를 모두 통과하는 배정을 끝까지 찾는다.
- 팀 4개 × 학생 8명이면 경우의 수가 4⁸ = 65,536이라 바로 끝난다. 정원, 주 역할 중복, 남은 학생 수로 가지치기한다.
- 배정이 없을 때의 이유는 팀마다 따져서 보여 준다.
  - 4명이 다 찼는데 필수 역할을 맡을 학생이 없음
  - 넣을 수 있는 학생 중에 그 역할을 맡을 학생이 없음
  - 전체 자리가 모자람
  - 빈 팀을 2명 이상으로 채울 학생이 모자람

## 7. 어려운 해결 선택(3장 표)

| 기능 | 선택 | 방법 |
|---|---|---|
| 다른 사람의 변경 보기 | 어려운 해결 | `st.fragment(run_every="3s")`로 바뀐 부분만 다시 그림 |
| 필수 포함 역할을 지킬 수 없는 팀 | 어려운 해결 | 지원 단계에서 6.1절 계산으로 막음 |
| 같은 팀에 대기 중인 지원이 여럿 | 어려운 해결 | 승인 직전 재검사(6.2절), 투표가 끝난 순서로 처리 |
| 마지막 자리에 두 명이 동시에 들어감 | 어려운 해결 | `tf_members`의 `(team_id, slot_no)` 기본 키와 `student_id` 유일 제약 |
| AI 응답이 늦을 때 | 어려운 해결 | 모델마다 부른 때부터 전체 120초를 재서 끊고 다음 모델로 넘어감 |
| 3차 모델까지 실패 | 어려운 해결 | 6.3절 완전 탐색으로 다섯 가지 검사를 통과하는 배정을 찾음 |
| AI 대기 중 화면 | 어려운 해결 | "2차 모델(모델 이름) 응답을 기다리는 중 (35초)"처럼 몇 차 모델인지 보여 줌 |
| DB 일시정지 막기 | 어려운 해결 | GitHub Actions 예약 실행으로 매일 DB에 질의 |

## 8. 비기능 요구사항

- **키 관리**: `OPENROUTER_API_KEY`, `DATABASE_URL`, `ADMIN_PASSWORD`는 로컬에서는 `.env`, 배포에서는 Streamlit Secrets에 둔다. 코드, 화면, 로그에 값을 쓰지 않는다.
- **성능**: DB 연결은 `st.cache_resource`로 한 번만 만들어 다시 쓴다.
- **시간**: 배정 전체가 10분을 넘지 않는다(모델 3개 × 120초 + 완전 탐색).
- **시각**: 화면에 시각을 보여 줄 때는 한국 시각으로 바꾼다.
- **정직성**: 연습용 시나리오의 학생 이름이나 순서를 보고 결과를 정하는 코드를 쓰지 않는다.
- **개인정보**: 실제 사람의 이름이나 학번을 쓰지 않는다.
